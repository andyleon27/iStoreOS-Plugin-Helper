## 当前菜单链的全部应用侧 HTTP 请求

顺序固定，全部由 **Windows 的 HttpWebRequest** 发出；SFTP 和 PTY 在三项下载及完整性校验之后才开始。

| 顺序 | 阶段 / 子阶段 | 方法与域名 | 请求 URL |
| --- | --- | --- | --- |
| 1 | Commit / ResolveMainCommit | GET api.github.com | `https://api.github.com/repos/slobys/openclash-auto-installer/git/ref/heads/main` |
| 2 | Download / DownloadMenu | GET raw.githubusercontent.com | `https://raw.githubusercontent.com/slobys/openclash-auto-installer/{SHA}/menu.sh` |
| 3 | Download / DownloadLicense | GET raw.githubusercontent.com | `https://raw.githubusercontent.com/slobys/openclash-auto-installer/{SHA}/LICENSE` |

`{SHA}` 是第 1 步解析得到的完整 40 位 commit，两项 Raw 下载使用同一个 SHA；原日志缺少它，不能把历史审计 SHA 当作本次 SHA。首页传入的 commit 为 null，所以“固定 SHA 下载”仍然先解析 main，而不是完全跳过 API。仅显式传入完整 commit 的内部入口才跳过第 1 步。

以上任意请求都可能被服务端或中间网关拒绝为 403。当前适配器不自动跟随重定向，不设置认证 token，不改系统 TLS，不自动重试。Windows 请求使用其现有 .NET/系统网络配置；路由器内 curl 能访问 GitHub，并不能证明 Windows 此请求路径可用。

## 已实现的诊断增强

业务流程保持原样，只增加失败上下文及日志格式：

1. 记录正在等待的应用侧请求 URL，区分 ResolveMainCommit、DownloadMenu、DownloadScript、DownloadLicense；成功返回后清空上下文，后续校验/SFTP 错误不误用前一次请求。
2. 从真实 `WebException.Response` 的 HttpWebResponse 读取状态码；对适配器返回的非 200 对象，只在原 IOException 的 Data 中附加状态码，保留异常类型、消息和拒绝行为。
3. 失败结果 Error 和维护日志同时携带阶段、目标域名、白名单 URL、HTTP 状态、异常类型；WebException 可附带枚举型网络状态。没有可用 HTTP 响应时为 `unknown`，不会猜测 403，也不遍历内部异常拼出状态。
4. 现有终端详情和首页保存日志沿用 Error，即可保留新诊断，无需改变 UI 业务代码。
5. 只输出精确公共 URL 白名单。非白名单地址的域名及 URL 均隐藏；不读/不输出响应正文、响应头、ResponseUri、原始异常消息、内部异常、代理配置、Cookie、Authorization、密码或 token。现有 SSH 密码脱敏仍继续生效。域名表示请求目标，并不能证明 403 的签发方就是该域名。


未新增重试、代理切换、认证 token、API 降级、HTTP 探测、菜单重发、证书绕过或脚本改写。原来的失败/取消/未知状态、互斥和清理规则均不改变。旧只读扫描的日志与上游脚本原始终端输出不在本轮改动范围。
