# 双 SSH 电脑代理隧道 POC 验证报告

2026-10-28（Asia/Taipei），独立宿主 R4；N1 `192.168.66.1:22`，Dropbear 2024.86；Windows HTTP 代理 `127.0.0.1:7897`。

两轮实机验证全部通过：专用 SSH #2 承载 `N1 127.0.0.1:17890 → Windows 127.0.0.1:7897`，两个目标均为 HTTP 200 / CONNECT 200 / TLS 校验 0。结束时自动断开并释放 #2，两轮均在首次检查时确认 17890 无监听，旧代理地址 curl 退出码为 7。首页 SSH #1 始终保留，无需用户断开或重新连接。

首轮 Windows 显式直连与本机代理的两个目标也均返回 HTTP 200。本轮重点验证独立 #2 的生命周期，没有再改变 N1 的路由或代理配置来制造对照；前轮 N1 直连 raw 超时的记录保留在旧报告。

**实现与连接边界**

首页 #1 是独立宿主内现有 MainForm / SshService 的客户端。POC 借用前复核连接、设备 Host Key 和空闲状态，并持有既有忙状态，避免安装、维护、用户断开并发。实验结束归还忙状态，不释放或替换 #1。

#2 通过现有 `connectionFactory` 创建新的 PasswordConnectionInfo，核对与 #1 相同的主机、端口和账户。它复用既有认证能力，不读取或记录密码字符串；拒绝复用 #1 的 ConnectionInfo 实例。Host Key 同时要求匹配当前设备指纹和已有 HostKeyTrustStore 中的主机/端口信任，不增加“自动信任新 Key”的路径。

反向转发仅添加到 #2。所有远端命令，包括 curl、监听检查和最终连接失败确认，都由 #1 执行；#2 只承载转发。N1 curl 的 http_proxy / https_proxy 只作用于该进程，保留 TLS 校验，清除继承的显式代理变量与 NO_PROXY 干扰，不写 curlrc 或其他配置。

finally 中明确断开并释放 #2，再由 #1 检查监听和旧代理端口。SSH.NET 的 [SshClient 源码](https://raw.githubusercontent.com/sshnet/SSH.NET/2026.0.0/src/Renci.SshNet/SshClient.cs)表明 Disconnect 内部仍可能先停止其转发；本实现不依赖单独取消转发成功，而是结束整个专用传输。前轮 Dropbear 取消转发的限制没有通过修改固件解决，其影响被限制在 #2 生命周期内。

首页健康检查覆盖创建 #2 前、连接 #2 后、转发启动后、每个目标 curl 后、关闭 #2 后及最终状态，共 7 个阶段。除 IsConnected 外，还验证实际命令响应、底层 session 对象身份和整个该段运行内的 ErrorOccurred 计数；不采用“断开后自动重连也算正常”的判断。

**复现步骤与风险**

1. 按 POC README 构建并打开可见 R4 宿主，在其助手窗口连接 N1 作为 #1。
2. 等待自动运行一次；确认两个目标为 HTTP 200、CONNECT 200、TLS 0，且 HostKeyValidated、SecondaryDistinct 为 true。
3. 确认 SecondaryDisconnected、After.Free、ClosedPortConfirmed 和 PrimaryAllChecksPassed 均为 true，清理错误列表为空。
4. 保持 #1 连接，提交固定 `run` 请求或点击单次验证，检查下一轮 Before.Free 和相同的成功条件。
5. 测试结束不必断开首页；`inspect-port` 可额外只读确认无监听，不会重建隧道。

实机结果覆盖当前一台 N1 / Dropbear 2024.86 的两轮正常关闭。异常、取消和身份变化已有离线用例，但其他设备、服务端转发策略及物理断网仍需单独实机验收。#2 额外占用一条 SSH 连接和相应资源；代理关闭、GitHub 限流或网络波动仍可能使请求失败。若 #1 同时失联，则无法通过它证明远端端口状态，结果会保留未知/失败标记。

POC 仍通过私有字段桥接产品认证和忙状态，属于实验代码耦合，正式集成前应改用明确接口。全程没有路由器永久代理、软件源、系统配置、固件或防火墙修改。
