最终主结果为 `TunnelVerified;PortReleaseNotVerified`，保持这一失败标记。后续通过结束所属 SSH 会话清理成功，不会把它改写成“保持 SSH 的取消转发已通过”。

故障定位到服务端取消转发路径。SSH.NET 的 [ForwardedPortRemote 源码](https://raw.githubusercontent.com/sshnet/SSH.NET/2026.0.0/src/Renci.SshNet/ForwardedPortRemote.cs)显示，Stop 发送取消请求，但公共 API 不暴露取消失败。实测的 Dropbear 版本为 2024.86；[该版本源码](https://raw.githubusercontent.com/mkj/dropbear/DROPBEAR_2024.86/src/svr-tcpfwd.c)中，取消匹配读取 `chantype`，取消请求结构却未初始化这个字段，而且监听地址在创建时还可能被规范化。这与当前取消失败相符，是源码层面的候选原因；本轮没有修改或替换设备二进制。

首轮 POC 还发现了诊断检查过严：Dropbear 为 IPv4 回环请求同时创建 IPv6 回环监听。已修正为允许 IPv4 加 `::1` 的组合，继续拒绝通配、LAN、重复和未知监听。R2 捕获到端口已被占用，正确拒绝再次创建或停止已有转发；后续 R3 在端口空闲时完成访问实测。

**实测复现步骤与风险**

1. 保持电脑 HTTP 代理运行，按 POC README 构建并打开可见的独立 R3 宿主。
2. 在该宿主的助手窗口手动连接 N1，等待自动单次对比；确认两个隧道请求均为 CONNECT 200、HTTP 200、TLS 0。
3. 核对 Before 空闲、During 只有回环；如果创建前占用，不停止已有监听。
4. 查看 Stop 后 After 是否空闲，以及旧代理地址 curl 是否退出 7；仅有 Stop 返回不足以验收。
5. 当前 Dropbear 2024.86 若出现同样的取消失败，先保存结果，再在独立宿主断开并重新连接；提交 `inspect-port` 请求，确认端口空闲且旧代理地址 curl 7。不自动复跑 `run`。
6. 完成后可关闭 POC 宿主；产品正常入口中没有增加此功能。

主要风险是共享 SSH 会话下无法可靠独立释放转发。当前 POC 的访问能力已证实，但停止语义尚不适合正式集成。电脑代理关闭、SSH 断线、服务端禁止转发、17890 已占用、代理认证、目标限流与网络波动也会影响结果；均以具体阶段和退出状态报告，不修改系统配置来恢复。
