## 上传链与判定规则

`.run / .ipk / .apk` → 现有独占 `/tmp/istore-plugin-helper/<GUID>/package.<扩展名>` → 优先 SFTP → 符合下述条件才尝试一次 SCP → 远端普通文件 / 非符号链接检查 → 大小一致 → 本地文件再次 SHA256 + 远端 SHA256 一致 → 原安装、快照、结果验证及清理流程。

SCP fallback 必须同时满足：

1. 错误发生在 SFTP 的 SSH 认证完成之后、subsystem 初始化期间，尚未进入文件写入。
2. 本次 SFTP 连接的 Host Key 已通过原有“设备地址 + 端口 + 已信任指纹”规则，认证成功，且没有收到 SSH transport 错误。
3. 异常的精确类型为 `SshException`、没有内部异常，消息精确匹配 `Channel was closed.` 或 `Subsystem 'sftp' could not be executed.`。
4. 失败的 SFTP 客户端已经释放，未取消，首页 SSH 仍在线；SCP 目标检查确认本轮目录存在且目标文件不存在（包括拒绝悬空符号链接）。

认证失败、Host Key 拒绝、密钥协商失败、连接断开、网络错误、超时、取消、权限错误、未知错误和上传过程中发生的通道关闭，均不会触发 SCP。规则对本项目固定的 SSH.NET 2026.0.0 保守匹配；未来库消息变化可能要求重新审查白名单。

SCP 通过正式 SSH 服务创建新的受信任传输客户端，使用相同连接工厂中的设备地址、端口、用户名和认证；再次核对现有 Host Key 信任。采用显式 `RemotePathTransformation.ShellQuote` 和 `UseDirectoryFlag=true`，传入路径仅由 `RemoteTempSession` 生成。不会执行本地文件名构造的远端命令，不安装额外服务、不修改设备 SSH/SFTP 配置。

实现依据：[SSH.NET BaseClient](https://github.com/sshnet/SSH.NET/blob/2026.0.0/src/Renci.SshNet/BaseClient.cs)、[SftpClient](https://github.com/sshnet/SSH.NET/blob/2026.0.0/src/Renci.SshNet/SftpClient.cs)、[SubsystemSession](https://github.com/sshnet/SSH.NET/blob/2026.0.0/src/Renci.SshNet/SubsystemSession.cs)、[ScpClient](https://github.com/sshnet/SSH.NET/blob/2026.0.0/src/Renci.SshNet/ScpClient.cs)。这些实现分别区分 SSH 认证、subsystem 初始化、transport 关闭和 channel 关闭；本项目在初始化回调内进行分类。

## 完整性、诊断与取消

- SFTP 与 SCP 共用后续校验；任一大小 / SHA256 不一致或远端文件不是安全普通文件，均禁止执行安装器。
- 按本轮“三种格式均必须通过 SHA256”的要求，`.run` 原有缺少 `sha256sum` 时继续依靠 Makeself 的分支改为停止；IPK/APK 原本已强制 SHA256。未安装补充工具。
- 丢失文件通过专用 exit 44 转为 `FileNotFoundException`，保留既有安装启动前重新上传能力；路径异常独立失败。
- 日志显示 `SFTP 上传完成`、`SFTP 不可用，自动切换 SCP 上传`、`SCP 上传完成`、`上传文件 SHA256 校验通过`。两种传输均失败时保留两个阶段的异常类型及有效消息，最终状态仍为 `FailedUpload`。
- 所有新上传诊断进入现有脱敏函数，不记录认证参数。异常汇总不附带未经脱敏的原始异常链。
- 取消关闭的仅是本次传输客户端；同步 SCP 上传退出并释放后才返回原流程。清理由原有编排层负责，未知安装器状态继续保留目录、禁止自动重复执行。

## R2S 实机验收与已知限制

**必须在真实 R2S / 24.10-snapshot / aarch64_generic / OPKG 复测；离线回归不能代替此项。** 本轮没有连接或写入真实设备。

1. 保持原设备不带 SFTP subsystem 的状态，确认 SSH 和 package update 正常；只读检查 `command -v scp`、`command -v sha256sum`。
2. 使用确实兼容设备的本地 IPK，以及已有可信的 24.10 架构匹配 `.run` 分别测试；OPKG 设备上的 `.apk` 应继续在兼容性阶段拒绝。
3. 核对日志顺序：SFTP 初始化不可用 → 自动切换 SCP → SCP 完成 → 大小 / SHA256 通过 → 原安装链；不得出现因首次上传失败自动重复执行安装器。
4. 上传期间取消，确认未启动安装器、传输已结束、本轮临时目录按原流程清理、首页 SSH 保持可用；网络失败应停止，不转为另一种上传重试。
5. 在具备正常 SFTP 的 N1 复核仍只使用 SFTP。原生 APK 的 SCP 实机安装需要另一个 APK 设备，不能以 OPKG 上的兼容性拒绝代替验收。

**重要限制：现有安装后日志 / exit.code 监测仍使用 SFTP，本轮遵照范围没有改写这一逻辑。** 因此在完全缺少 SFTP 的设备上，即使 SCP 上传及完整性校验成功，安装器启动后仍可能因日志通道不可用而进入 `InstallerStateUnknown`，保留现场且禁止自动重装。不得据本轮上传测试宣称 R2S 完整安装链已验收通过；发布前还需要确认此行为，并确定是否在后续范围内补充日志监测兼容方案。

设备还必须具备可用的远端 `scp` 命令；缺失或被 SSH 服务禁止执行时，双失败会显示有效诊断并保持 `FailedUpload`。SCP 操作超时为 60 秒，保留原连接超时和既有安装监测限制。本轮未变更插件维护终端、电脑代理、软件源、安装器命令或包快照实现。
