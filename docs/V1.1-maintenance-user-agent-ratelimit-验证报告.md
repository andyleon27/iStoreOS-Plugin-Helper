## 结论

`ThirdPartyScriptSource.cs` 的 Windows HTTP 客户端已经设置固定、非空的应用名 User-Agent：

```text
User-Agent: iStoreOS-Plugin-Helper-Phase2A
```

设置发生在发送请求之前，对 main API、menu.sh 和 LICENSE 请求都生效。现有 `Accept` 未显式设置。用户指令中“如果未设置有效 User-Agent”分支不适用，因此本轮没有更改 User-Agent，也没有改变 Accept、代理、TLS、超时、重定向或重试策略。

[GitHub 官方文档](https://docs.github.com/en/rest/using-the-rest-api/getting-started-with-the-rest-api#headers)允许以应用名作为 User-Agent，并推荐 Accept 为 application/vnd.github+json。此次使用现有 User-Agent、未显式设置 Accept 的实际请求获得 HTTP 200，因此本次观测不支持“当前代码缺失 User-Agent 导致 403”的解释。此前两次失败的请求头及限流头未保存，仍不能据此确认历史失败的根因。

- 缺少或不可信头值时，状态应继续待确认。本程序不根据这些诊断自动重试、等待、切换代理或修改认证。

响应头只是收到的证据，不能单独认证响应签发方，也不能单靠数字排除中间网关。

## 诊断改动

保留已有阶段、域名、白名单 URL、HTTP 状态码、异常类型和网络状态。仅针对精确 main API URL 的 403/429，追加：

```text
x-ratelimit-remaining=<非负整数或 unknown / [invalid]>
x-ratelimit-reset=<非负整数或 unknown / [invalid]>
```

只读取这两个响应头。缺失值为 unknown；仅接受长度受限的 ASCII 十进制非负 Int64，进行规范化后输出；逗号合并的重复值、符号、溢出、非数字、过长内容等记为 [invalid]，不回显原值。reset 记录为数值证据，不在业务层自动解释或触发动作。

Raw 下载失败、非白名单 URL、其他 HTTP 错误和无响应错误不被解释为 API 配额问题。响应正文、其他响应头、Cookie、Authorization、代理、凭据和任意异常消息仍不会进入新增诊断。错误沿用已有 Error / 维护日志 / 首页保存日志路径，无需修改首页业务代码。

为离线验证实际请求对象，将原有请求构造代码原样提取成内部 CreateRequest 方法；实际发送调用该方法。请求头赋值和所有网络策略原样保留。
