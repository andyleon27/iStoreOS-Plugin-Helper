## 上游来源、固定 commit 和真实映射

每次准备先请求：

`https://api.github.com/repos/slobys/openclash-auto-installer/git/ref/heads/main`

响应必须是 `refs/heads/main`、目标类型 `commit`，并包含完整 40 位 SHA。不会把 `main` 当作最终来源版本；不使用大型 commits 响应、不自动更新本地引擎或长期缓存版本。每个任务只解析一次，把这个不可变 SHA 写入描述模型，后续脚本和 LICENSE URL 均从同一个描述生成：

`https://raw.githubusercontent.com/slobys/openclash-auto-installer/<完整 SHA>/<文件名>`

| 插件 | 安装 / 更新入口 | 更新参数 |
| --- | --- | --- |
| OpenClash | install.sh | 更新预览使用上游菜单采用的 `--plugin-only` |
| PassWall | passwall.sh | 默认原脚本行为 |
| PassWall2 | passwall2.sh | 默认原脚本行为 |
| Nikki | nikki.sh | 默认原脚本行为 |
| SmartDNS | smartdns.sh | 默认原脚本行为 |
| MosDNS | mosdns.sh | 默认原脚本行为 |
| daed | daed.sh | 默认原脚本行为 |

检查映射到 `check-updates.sh --<插件名>`；卸载映射到 `uninstall.sh <插件名>`，默认不附删除配置参数，只有显式选择才在预览中增加 `--delete-config`。这些命令只生成字符串，不传给 SSH。

核对来源为[上游项目](https://github.com/slobys/openclash-auto-installer)在修订 `9a576f1e67512c1f6c6d932191ba3c6a7fd27661` 的原始脚本和菜单。没有使用会再次拉取 main/install.sh 的 update.sh 包装入口，没有修改任何第三方脚本。

固定范围是**本工具在该任务下载的维护脚本与 LICENSE**。未来脚本自己访问的外部版本、依赖和其它仓库不会因此全部固定；例如原 Nikki 脚本引用其自身项目的 main 脚本。本阶段没有执行它，也没有为固定这些内部访问而 patch 上游；后续开放执行前应继续如实说明这一边界。

Phase 1 原有固定 LICENSE HEAD 仍仅用于轻量连通检测，本轮保持不变；Phase 2A 脚本准备会另外解析本次 main，不长期绑定该检测参考 SHA。

## 门禁、单任务和日志

真实 SSH 接入要求当前连接刚经 Phase 1 返回 Ready / OnlineAvailable。该结果只在 SshService 的维护读取入口内记录，并绑定同一个 SshClient；新检测开始先撤销旧批准，不同 / 断开的连接不能复用。使用弱引用避免额外延长已关闭连接及凭据的生命周期。准备还要求原设备指纹仍在受信任表中；SFTP 复用原有指纹验证，不启用 SCP 或弱身份回退。

服务内部用 `SemaphoreSlim(1,1)` 非阻塞获取单任务锁，重复请求返回 Busy；锁一直覆盖到清理完成。SshService 同时使用既有 busy 互斥，不能与检测、未结束安装或原 `.run` 流程争用连接。维护失败只返回维护准备结果，不调用安装 / 软件源 / 恢复逻辑。

每条日志含 OperationId 和来源，准备阶段仅使用 `[Plugin Helper]`。`[Third-party Script]` 只预留给未来真实 stdout / stderr，不伪造第三方输出。新日志缓冲区拒绝旧任务 ID，避免旧回调覆盖后续任务。日志包括项目、Repository、main + 实际 SHA、脚本、下载 URL、SHA256、远端路径、完整性、执行禁用与清理结果；密码沿用现有脱敏函数。

## 获取、hash、上传和清理

- Windows HTTP：仅允许官方项目的 main 引用 API 和完整 SHA raw 白名单文件；必须 HTTP 200，不跟随重定向、不使用 token、不放宽证书检查、不改全局 TLS。沿用 .NET Framework 4.8 的系统 TLS 默认值；请求禁用缓存，整体限时 25 秒。脚本上限 1 MiB，LICENSE / 引用响应上限 64 KiB，读取流同样限长。
- 不修改下载字节。拒绝空文件、HTML / 二进制 / 非预期 shell header；读取并验证同一 SHA 的 MIT LICENSE 和版权。若上游许可不符，停止而不是静默替换。
- Windows 在系统临时目录创建独立 `iStoreOS.PluginHelper-maintenance-<任务ID>`，仅写入本次原脚本、原始 LICENSE 和来源 NOTICE.txt。逐个用 `SHA256.Create()` 计算完整文件 hash。
- 路由器仅在 `/tmp/istoreos-plugin-helper/maintenance-<任务ID>/` 工作。使用 `umask 077`、唯一目录及 `.owner` 标记，SFTP 不覆盖已有文件，不赋予脚本执行权限。
- 上传三份文件后逐个调用 `sha256sum`；输出必须匹配本次精确文件路径，且与 Windows hash 相同。缺少 sha256sum、输出异常或不一致都拒绝进入准备完成状态，不安装 hash 工具。
- 完成后仅生成 `sh '<临时脚本>' '<参数>'` 的命令预览。`ExecutionEnabled` 恒为 false，`ExecuteScriptAsync` 永远拒绝，SSH 会话接口没有脚本执行方法。
- 随即清理：Phase 2A 返回的是追溯结果和不可执行预览，**不是保留在远端等待执行的句柄**。清理后预览路径已不存在，不能跨任务复用。
- Windows 清理仅删除已知三文件及本次空目录，不递归删除、不删除其它缓存 / 配置，遇到重解析点或锁定文件明确报告失败。
- 远端先验证任务路径不是符号链接、归属标记匹配，再精确删除已知文件及标记，用 rmdir 删除空任务目录；最后尝试 rmdir 空父目录，不用 rm -rf。
- 失败、取消、SSH 中断同样尝试清理。用户取消不会取消清理：清理使用独立的 20 秒 token，SSH 命令本身限时 15 秒。不能清理时保留失败标记、具体目录与告警，不谎报成功；不会为清理自动重连到身份不确定的设备。
