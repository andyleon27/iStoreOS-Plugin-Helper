## A. 环境和候选包

- [ ] A1 在 Windows x64、.NET Framework 4.8 环境记录本次 EXE SHA256；如使用新候选 ZIP，再校验 ZIP 与本次 SHA256SUMS 一致。使用独立目录，不覆盖旧版本；EXE、13 个运行时 DLL、config 齐全，项目及第三方许可文件可供核对。
- [ ] A2 启动 EXE。首页布局正常，密码初始隐藏，未连接时“安装插件”和“插件维护”禁用。当前显示 V1.0.2 是候选的已知版本标识，验收必须同时核对本次 ZIP 哈希。
- [ ] A3 在 N1 保存现有配置备份、插件及软件源基线。选择有线连接和允许测试的设备；真实安装/更新/卸载会改变设备，卸载可能删除配置。
- [ ] A4 填写当前固件/架构和包管理器，确认 Windows 与 N1 的代理/GitHub 路径均符合上游脚本运行要求。按钮启用不代表 GitHub 已连通。

可在独立 SSH 管理终端做以下只读核对；不要把这些命令输入原项目的数字菜单：

~~~sh
cat /etc/openwrt_release
uname -m
test -r /proc/self/stat && cat /proc/self/stat
date +%s
for tool in sh sha256sum wc cat date mv rm rmdir; do command -v "$tool"; done
if command -v opkg >/dev/null 2>&1; then opkg print-architecture; opkg list-installed; fi
if command -v apk >/dev/null 2>&1; then apk --print-arch; apk info; fi
for file in /etc/opkg/distfeeds.conf /etc/opkg/customfeeds.conf /etc/apk/repositories /etc/apk/repositories.d/distfeeds.list /etc/apk/repositories.d/customfeeds.list; do
    test ! -f "$file" || sha256sum "$file"
done
~~~

## B. 首页和首次安装链

- [ ] B1 从首页连接 N1，核对当前固件、SDK、原始架构、包管理器和 Host Key 指纹。密码输入框在连接后清空；高级信息可读，未发生重复认证或指纹绕过。
- [ ] B2 连接成功且空闲时“插件维护”启用。连接/软件检测/首次安装任务期间禁用；存在待确认的旧安装任务时禁用。等当前任务完全结束后才恢复。
- [ ] B3 选择可信、与当前 N1 SDK/架构兼容的本地 `.run`，核对 Compatible。用错误 SDK 或明确不兼容架构的文件作反例，安装按钮应禁用，不能实际执行反例。
- [ ] B4 在允许写入的测试设备上，选择一个明确指定的插件执行首次安装。保留预检、update gate、上传/hash、runner、包变化、独立安装验证及清理日志；成功必须是实际 SuccessVerified，而非看到 SUCCESS 字样。
- [ ] B5 核对成功后保留选中的可用软件源这一当前 V1 行为；失败时沿用原恢复策略。记录操作前后源与插件变化，不把预期的源保留误当回归。
- [ ] B6 如在准备阶段取消，确认退出准备并清理；安装器已派发后不强行中止或拔电。故障恢复、换源失败和旧 runner 恢复若未在隔离设备执行，标记未执行，不为覆盖测试而损坏现有源。

## C. 新菜单终端与任务身份

- [ ] C1 空闲时从首页点“插件维护”，只出现一个新终端窗口，不出现旧七插件按钮表。窗口自动准备并启动原项目菜单；连接状态、菜单状态与来源/版权说明可见。
- [ ] C2 打开时首页作为 owner 保持可见，暂不可操作；重复点击或快捷键不应启动第二份菜单。准备失败应显示原因，不自动重试，不断开首页 SSH。
- [ ] C3 在菜单未选择写操作时，测试中文显示、回车、方向键/退格、复制选区、粘贴无害输入、滚动后回到底部和窗口缩放。Ctrl+C 有选区时复制；无选区时向 PTY 发送中断。不要粘贴未知 Shell 命令或安装选项。
- [ ] C4 在独立管理 SSH 中记录本次 `/tmp/istoreos-plugin-helper/maintenance-<任务ID>` 的 `.owner`、`menu.pid`、`menu.start`、NOTICE.txt 和四文件 SHA256。核对任务 ID、运行 ID、launcher PID、进程启动 ticks、Unix 启动时间；与窗口 PID 一致，`/proc/<PID>/stat` 可读。
- [ ] C5 按 NOTICE 中的 `Ref: main`、两个 Raw 下载 URL 和未解析 commit 的标记核对来源，准备日志不应出现 main API 请求。任务活跃时 Windows `%TEMP%\iStoreOS.PluginHelper-maintenance-<相同任务ID>` 中的 menu.sh、LICENSE、NOTICE.txt、helper-launcher.sh 应与 N1 四文件 hash 一致。main 两次下载不保证同一 commit，SHA256 验证的是本次字节的传输完整性；仅显式固定 SHA 入口才核对完整 commit。不要修改原脚本或 launcher。
- [ ] C6 通过原菜单自己的退出选项正常退出，最后一行完整显示，窗口显示“菜单已正常退出”，SSH 状态仍为已连接。本次任务目录应清理；其他历史/相邻任务目录不得被删除。
- [ ] C7 返回首页后立即重新打开菜单，生成新的任务/运行 ID，不能复用上次清理后的目录；再正常退出并返回，首页 SSH 仍可用。

若没有正常退出选项或菜单行为与预期不同，先记录实际提示，不猜测数字选项。上游菜单启动时可能自行做检查或下载；“未选择安装”不等于保证设备零变化。

## D. 关闭、退出分类与断线

- [ ] D1 在下载/准备期间返回首页。等待“正在返回”完成，确认无菜单被派发，首页 SSH 不受影响，下一次可重新打开。
- [ ] D2 仅在菜单空闲时分别测试“返回首页”和标题栏 X。窗口等待读写结束、状态复核及允许的清理后关闭；重复关闭不出现重复任务。不能把关闭窗口当成已经停止远端插件动作。
- [ ] D3 对 Ctrl+C 的实际行为作记录：可能返回菜单、非零退出或最终未知；结果必须与证据一致。没有相符退出记录时不能显示成功，未知任务目录应保留并将路径写入首页日志。
- [ ] D4 如上游菜单自然产生已知非零退出，核对错误退出码与“菜单异常退出”；保留完整输出。不要改写原始下载脚本来强造退出码。无法安全触发的非零退出项标记未执行，离线合成测试不替代实机记录。
- [ ] D5 在菜单空闲、未执行安装/卸载时，临时断开 Windows 到 N1 的连接。窗口应显示断线/未知，不自动重连重发菜单，不做无依据清理。首页维护入口随后禁用，即使仍缓存可重连凭据。
- [ ] D6 恢复网络，人工重新连接并核对设备身份；先在独立管理终端确认旧任务是否仍运行，不盲目重复相同插件动作。新的窗口必须使用新任务 ID。保留旧未知任务和日志供核查。
- [ ] D7 Host Key 变化拒绝仅在隔离 SSH 测试端点验证；不要为该项重建生产 N1 的 SSH 密钥。不一致时应拒绝，不能继续 SFTP 或 PTY。未执行则保留为离线覆盖项。

正常退出时目录缺失符合预期；未知状态时目录保留符合预期。不要对未知任务执行 `rm -rf` 或只凭 PID 数字杀进程，先核对任务/运行 ID 和 startTicks。不要在安装、更新或卸载过程中人为断网来完成本表。
