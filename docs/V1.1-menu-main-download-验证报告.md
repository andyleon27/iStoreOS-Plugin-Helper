# 菜单准备改为 upstream main 直接下载

日期：2026-10-28（Asia/Taipei）。本轮完成实现、离线测试、Release x64 构建及完整回归，没有向 GitHub 发出真实请求，没有连接路由器或执行上游脚本。

## 修改后的默认启动链

首页“插件维护”仍打开原项目菜单终端。默认 `PrepareMenuAsync` 和 `RunMenuAsync` 不再调用 `ResolveMainCommitAsync`，也不发出 main SHA API 请求。

1. 复核已有 SSH、认证与 Host Key 身份，取得现有软件任务互斥；首页忙状态和未确认安装任务的 Gate 保留。
2. Windows 顺序 GET 两个精确白名单 URL：
   - [menu.sh](https://raw.githubusercontent.com/slobys/openclash-auto-installer/main/menu.sh)，最大 1 MiB。
   - [LICENSE](https://raw.githubusercontent.com/slobys/openclash-auto-installer/main/LICENSE)，最大 64 KiB。
3. 沿用脚本内容、UTF-8、shell 头、大小及已知 MIT 许可信息检查；下载失败或内容不合法即停止，不创建远端工作区，不启动菜单，不回退到其他来源。
4. 建立独占本地任务目录，保留原下载字节，生成 NOTICE 和原有 helper-launcher.sh；计算这四个文件的本地 SHA256。
5. 创建具有任务所有权标记的独立 `/tmp/istoreos-plugin-helper/maintenance-<任务ID>`，通过既有认证和 Host Key 校验的 SFTP 上传四个文件。
6. 逐项读取远端 SHA256，严格核对文件路径和 hash；任一不一致都拒绝创建菜单 PTY。
7. 在现有 SSH 连接上打开独立 ShellStream / PTY，以原有短命令启动 launcher，由 launcher 执行原始 menu.sh。菜单启动后的上游版本解析、下载、安装、更新、卸载和交互继续由原始脚本处理，助手不代替解析、不改写脚本。
8. 沿用 PID、进程启动 ticks、Unix 时间及退出状态协议，排空终端最终输出后确认状态；只有满足既有结束证据和所有权条件才清理。未知状态保留目录。关闭终端只关闭菜单通道，不主动断开首页 SSH，也不据此宣称远端任务已停止。

默认菜单的应用侧 HTTP 数量由 3 次减少为 2 次，均为 Raw 文件 GET，不再包含 `api.github.com`。此变化不限制 menu.sh 启动后自行发起的上游请求，也不保证后续脚本完全不依赖 GitHub API。

显式传入完整 SHA 的菜单入口继续保留：只下载该 SHA 下的两个文件，本来就不需要解析 main API。旧单插件维护路径继续沿用原有 SHA 解析和固定下载行为；首次安装 `.run` 链未修改。

## 来源记录与边界

默认菜单描述符为 `SourceRef = main`、`Commit = null`。日志与 NOTICE 明确记录：

```text
Ref: main
Commit: not resolved (direct branch download)
Download URL: https://raw.githubusercontent.com/slobys/openclash-auto-installer/main/menu.sh
License URL: https://raw.githubusercontent.com/slobys/openclash-auto-installer/main/LICENSE
```

main 是可变引用，两次请求可能遇到分支更新，不能再保证两个文件来自同一个 commit。本轮没有伪造 commit，也没有暗中发 API 请求补齐它。本地及远端 SHA256 识别并核对本次收到的字节，用于传输完整性，不等同于上游签名验证或固定版本保证。

白名单只新增上述两个**完整、精确**的 main URL；其他 main 脚本、launcher、运行状态文件、其他仓库、HTTP、带凭据/查询/fragment/端口的变体、大小写或路径变体均不放行。已有完整 SHA URL 白名单仍保留。

下载仍使用原 User-Agent、缓存策略、大小/时间上限、系统 TLS 和证书验证；不跟随重定向、不自动重试、不修改代理、不新增 token。原阶段/域名/URL/HTTP 失败诊断与脱敏逻辑保留：Raw 403 会标明 DownloadMenu 或 DownloadLicense，不被解释为 API 配额问题。API 限流头诊断仍可服务于保留的旧单插件路径。

独占任务、互斥、输入输出、EOF 排空、正常/异常/未知退出、断线、Host Key、所有权、软链接防护、文件白名单、未知文件保留和邻居任务隔离等安全边界未改变。
