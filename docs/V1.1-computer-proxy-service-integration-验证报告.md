# 电脑代理双 SSH 服务层正式集成

后续入口集成已将 GitHub Raw 改为唯一网络 Gate，GitHub API 仅作诊断，并接入维护 UI。本文保留当轮服务层测试记录；当前行为见 [最终维护入口报告](C:/Development/iStoreOS-Plugin-Helper/docs/V1.1-maintenance-launch-network-验证报告.md)。

本轮已将双 SSH 隧道能力纳入产品服务层，提供创建、验证和关闭接口。独立 SSH #2 承载反向代理隧道，首页 SSH #1 负责只读检查与 curl；认证与 Host Key 由 SshService 内部正式提供，生产实现不读取私有字段、不引用 POC 类型。

首页、插件维护按钮、窗口、安装流程、menu.sh 准备及执行链均未修改。当前没有 UI 入口自动启用隧道，也没有重新加入 GitHub API main SHA 解析。API 请求仅用于隧道可达性验证，响应体被丢弃。

**正式接口**

| 接口 | 行为 |
|---|---|
| `WindowsComputerProxyDetector.GetListeningCandidates()` | 只读获取 Windows 本地监听代理候选端口；候选不等于已验证的 HTTP 代理 |
| `SshService.CreateComputerProxyTunnelAsync(router, port, progress, token)` | 复核设备身份和互斥，创建专用 #2 并建立固定回环转发；成功返回 Ready，持有忙状态 |
| `VerifyComputerProxyTunnelAsync(token)` | 通过 #1 对两个白名单目标执行临时代理 curl；分别检查 HTTP、CONNECT 和 TLS，均符合才返回 Verified |
| `CloseComputerProxyTunnelAsync()` | 幂等、不可由调用者取消的清理；关闭并释放 #2，由 #1 确认端口释放及连接失败，再归还忙状态 |
| `HasComputerProxyTunnel` / `ComputerProxyEndpoint` | 当前隧道是否持有及目标快照；不暴露认证材料 |
| `LastComputerProxyClose` | 保存自动或显式关闭的资源、端口、首页健康和错误类型结果 |

调用方需要完整持有创建至关闭的生命周期，例如：

```csharp
var opened = await ssh.CreateComputerProxyTunnelAsync(router, proxyPort, progress, token);
if (opened.Outcome == ComputerProxyOutcome.Ready)
{
    try
    {
        var verified = await ssh.VerifyComputerProxyTunnelAsync(token);
        // 此轮只提供服务能力，尚未编排插件维护调用。
    }
    finally
    {
        var closed = await ssh.CloseComputerProxyTunnelAsync();
        // 检查 closed.Succeeded / Release / PrimaryHealthy。
    }
}
```

创建失败、验证失败、验证取消和连接错误会自动进入关闭流程。显式关闭可与准备或验证并发：先取消在途操作，等待串行操作门退出，再清理 #2。重复关闭只执行一次清理，旧任务不会清除后来操作的忙状态。SshService 整体 Dispose 时，也先处理 #2，再结束首页 #1。

**身份与安全边界**

SshService 在现有锁内捕获当前设备地址、端口、账户、认证工厂和设备指纹；新连接使用独立 PasswordConnectionInfo 和独立 SshClient。地址、端口或账户不一致、返回首页 ConnectionInfo 别名、Host Key 不匹配已有设备指纹或已有主机/端口信任时均拒绝。认证工厂和信任回调只进入内部上下文，不通过公共 API 暴露密码、客户端或可执行凭据工厂。

反向转发固定为 `N1 127.0.0.1:17890 → Windows 127.0.0.1:<候选代理端口>`。允许 Dropbear 同时产生 IPv4 和 `::1` 回环监听，拒绝 LAN、通配、重复、未知监听。端口预先占用或状态无法读取时拒绝创建，不停止已有监听、不杀进程。

结束 #2 的整个 SSH 生命周期，避免依赖 Dropbear 单独取消转发成功。关闭后通过 #1 读取 `/proc/net/tcp*`，并要求旧代理地址 curl 返回连接失败。首页可用性同时检查现有服务客户端身份、连接错误事件和实际命令响应；没有通过自动重连来掩盖断线。

释放结果区分 `NotCreated`、`Released`、`StillListening` 和 `Unknown`。只有 #2 已确认关闭、端口无监听、旧代理地址连接失败、首页健康且无清理错误，已创建隧道的关闭才报告 Succeeded。首页同时断线或状态读取失败时保留 Unknown；客户端 Dispose 或 Stop 返回本身不足以宣称端口已释放。

远端命令由枚举映射为固定白名单，不接受任意 URL 或 Shell 文本。仅测试 curl 进程设置 http_proxy / https_proxy，清除继承的其他显式代理变量和 NO_PROXY，使用 `curl -q`；保留 TLS 校验、不跟随重定向、不写代理、软件源、系统或 curl 配置。GitHub API 使用固定 User-Agent 和 `Accept: application/vnd.github+json`。

日志只包含阶段、固定公共域名/URL、HTTP 状态、curl 退出码、有限错误代码及异常类型；不记录原始异常消息、密码、令牌、Cookie、完整响应头或响应体。API 限流头只保留数值。HTTP 403 与 CONNECT 407、TLS 失败、超时分别判定，日志消费者抛出异常也不会绕过资源清理。

**风险与后续验收**

- 本轮是正式服务层的离线集成与回归，没有新做正式 API 的 N1 实机运行；前轮 [双 SSH POC 两轮实测](C:/Development/iStoreOS-Plugin-Helper/docs/V1.1-computer-proxy-dual-ssh-poc-验证报告.md)验证了独立 #2 关闭可释放当前 N1 的监听，不能将它记作本轮新代码的实测。
- 当前隧道从创建至关闭持有忙状态。后续接入插件维护时，需要统一编排隧道和维护任务生命周期，不能直接在持有隧道时并行调用现有维护入口。本轮按要求没有改 UI 或按钮。
- 本机监听只是候选；HTTP 代理类型、HTTPS CONNECT、目标站点和限流需由 Verify 检查。N1 需要已有 curl 和可读的 Linux TCP 状态，不会自动安装或修改服务端策略。
- 若首页也断线，#2 仍会清理，但远端释放可能无法确认；必须保留 Unknown。服务端关闭耗时、网络异常和其他固件行为仍需实机覆盖。

正式服务的实机验收应执行：连接首页 #1 → 获取本机候选 → Create 返回 Ready → Verify 两目标均 HTTP/CONNECT 200、TLS 0 → Close 为 Succeeded/Released/PrimaryHealthy → 再创建一次确认端口复用；同时验证取消、电脑代理退出和网络断线时不会误断 #1 或误报端口释放。该流程尚未加入产品 UI。
